# Community Effect lint survey

Audit date: 2026-08-30

## Question and selection

This survey asks a narrow question: what do current, non-Effect-TS Effect applications and libraries actually enforce with Oxlint, Biome, ESLint, the Effect language service, and `@effect/tsgo`, and which of those checks should influence Effect Doctor?

The primary sample is every repository listed by [`jeremyosih/real-world-effect` at `a5b4021`](https://github.com/jeremyosih/real-world-effect/blob/a5b40213dafad32d7ce96ccecef88a17b8031b40/repos.md). That catalog requires meaningful Effect use and either active maintenance or code worth studying; its seven entries are applications rather than tutorials. Each entry below was then inspected at its own current default-branch revision, not at the submodule revision stored by the aggregator.

After completing all seven, the survey expanded to repositories with unusually strong evidence: an active, production-sized adopter of the new `@effect/tsgo` Oxlint bridge, a published Effect-specific lint plugin, or a custom rule family with an explicit contract. The expanded sample is intentionally evidence-seeking, not a popularity ranking or an estimate of ecosystem adoption.

Configuration and scripts were read in full where they existed. Repository-wide path and dependency searches were used to record absence as well as presence. Generated files, vendored reference checkouts, and `node_modules` were excluded.

The complete catalog therefore has two custom-Oxlint adopters (`t3code`, `executor`). Beyond those two, three projects use some form of Effect language-service configuration (`AnswerOverflow`, `r8y`, `better-context`), while two have no Effect-specific analyzer (`course-video-manager`, `expect`). This diversity is important: a Doctor default cannot assume one repository's testing library, import style, entrypoint wrapper, file layout, or migration state.

## Expanded high-signal sample

### Official type-aware rules are becoming the common semantic layer

Several current applications now patch Oxlint with `@effect/tsgo` and extend its presets rather than recreating semantic rules:

- Supabase CLI scopes the official recommended preset to its Effect packages in [`.oxlintrc.effect.json`](https://github.com/supabase/cli/blob/7a16903c7b39fb7e4f01e03339c3c2b7dafc256b/.oxlintrc.effect.json), while its ordinary config retains broad TypeScript checks and documents Effect-specific false-positive exceptions in [`.oxlintrc.json`](https://github.com/supabase/cli/blob/7a16903c7b39fb7e4f01e03339c3c2b7dafc256b/.oxlintrc.json).
- Maple extends the recommended preset and explicitly promotes or demotes individual `effecttsgo/*` diagnostics in [`.oxlintrc.effect.json`](https://github.com/MapleTechLabs/maple/blob/b944cb99d6ae046f81d1f4725793b9edaa5d26f1/.oxlintrc.effect.json). Its three-rule [local plugin](https://github.com/MapleTechLabs/maple/blob/b944cb99d6ae046f81d1f4725793b9edaa5d26f1/scripts/oxlint-plugins/maple.mjs) contains one Effect rule, but that rule protects Maple's own ClickHouse compilation seam and explicitly names its internal APIs.
- `effect-grammar` extends the official recommended config in [`oxlint.config.ts`](https://github.com/saiashirwad/effect-grammar/blob/6265dd3f1441ba3e29e2385181817cfaf0503a4c/oxlint.config.ts), then carries a local [`no-service-constructor-imports`](https://github.com/saiashirwad/effect-grammar/blob/6265dd3f1441ba3e29e2385181817cfaf0503a4c/tools/oxlint/anti-slop/effect/rules/no-service-constructor-imports.ts) convention based on project-local `makeX` names.
- Company OS deliberately extends only the official correctness preset, then selects additional diagnostics in [`.oxlintrc.json`](https://github.com/continual-ai/company-os/blob/77115ba42db84dba4ae7187cac5deb062c1291f5/.oxlintrc.json).
- System F's shareable config also extends only the official correctness preset and explains why it rejected the 78-rule recommended set as too noisy for its tree in [`oxlint-config.base.ts`](https://github.com/systemfsoftware/systemfsoftware/blob/4f88cd855f219254dcc5c4760d261ad55a0e8b85/packages/lint/oxlint/config/src/oxlint-config.base.ts). It layers narrowly scoped, separately published plugins over that semantic core.

This supports Effect Doctor's existing ownership boundary: `@effect/tsgo` should continue to own type-aware Effect semantics. Community severity choices are calibration evidence, not grounds to clone those diagnostics as first-party AST rules.

### Custom rule families are mostly architecture, not universal Effect correctness

- DXOS enables `@effect/tsgo`'s Oxlint schema and type-aware mode, but its custom [`no-effect-run-promise`](https://github.com/dxos/dxos/blob/f7b292fb975ce0cc28f336ebc15be23c58952b1c/packages/common/eslint-plugin-rules/rules/no-effect-run-promise.js) rule redirects callers to the DXOS-specific `EffectEx.runPromise`. Its [`effect-subpath-imports`](https://github.com/dxos/dxos/blob/f7b292fb975ce0cc28f336ebc15be23c58952b1c/packages/common/eslint-plugin-rules/rules/effect-subpath-imports.js) rule is an autofixing import convention. Neither expresses a universal Effect failure.
- System F publishes strong, thoroughly tested rules, but the contracts are explicitly architectural: `main.ts` must be a single interpretation edge in [`effect-entrypoint`](https://github.com/systemfsoftware/systemfsoftware/blob/4f88cd855f219254dcc5c4760d261ad55a0e8b85/packages/lint/oxlint/plugins/effect/entrypoint/README.md), and schema declarations must live in prescribed files in [`effect-schema`](https://github.com/systemfsoftware/systemfsoftware/blob/4f88cd855f219254dcc5c4760d261ad55a0e8b85/packages/lint/oxlint/plugins/effect/schema/README.md). These are valuable optional policy plugins, not black-box quality invariants.
- Effect Machine publishes a conservative [Oxlint plugin](https://github.com/typeonce-dev/effect-machine/blob/78699917a7fd385dbf86b8c03070be12d269d3d5/packages/oxlint-plugin/README.md), but its rules protect the planning semantics of that library's `Machine.make` DSL. Effect Doctor should not absorb them; a project scan can run that plugin separately when Effect Machine is present.
- Solstatus registers `@mpsuesser/oxlint-plugin-effect` in [`.oxlintrc.json`](https://github.com/jonbeckman/solstatus/blob/3ab6ebebf27e4b9f945aa8f5760643643b110b30/.oxlintrc.json), but the configuration enables no `effect/*` rule; it only switches two such names off in overrides. The actually enabled Effect-flavored custom rule is the naming-based `anti-slop-effect/no-service-constructor-imports`. Plugin presence alone is therefore not evidence that its rules are enforced.

## Candidate and rejection matrix

| Community rule or pattern | Decision for Effect Doctor | Rationale |
| --- | --- | --- |
| Hoist immediately invoked `Schema.is` / decode / encode compiler creation out of function bodies | **Research as a first-party advisory candidate.** | `t3code` and `executor` independently implemented almost the same rule. A portable contract can be narrower than either implementation: resolve the actual `effect/Schema` binding, require a statically reusable schema expression, and report only an immediately invoked compiler created inside a function. Dynamic schemas and returned compiler functions must remain valid. Before adoption, confirm allocation semantics against official Effect source and calibrate on the corpus. |
| Prohibit `Effect.runPromise` in tests | **Reject as universal.** | `t3code` needs a repository-specific legacy baseline, DXOS requires its own wrapper, and the official [`floatingEffectInVitest`](https://github.com/Effect-TS/tsgo/blob/f134c316b685b70fc513d10ed9b7c899088667f5/docs/rules/floating-effect-in-vitest.md) diagnostic itself treats `Effect.runPromise` as a valid way to execute an Effect in an ordinary Vitest callback. Prefer `@effect/vitest` is team policy, not correctness. |
| Ban `Effect.die` / `orDie`, `Schema.Class`, `Match.orElse`, all `switch`, all manual `_tag` checks, all Promise APIs, or all native `Error` values | **Reject as universal.** | These APIs have legitimate defect, boundary, representation, fallback, and interop uses. Executor's blanket versions are coupled to its domain architecture and extensive override map. Several also already have narrower upstream diagnostics. |
| `JSON.parse` to Schema, raw `fetch` to Effect HTTP, try/catch/throw avoidance, `new Error`, and direct globals | **Delegate to existing providers.** | Effect Doctor already catalogs `effect/prefer-schema-over-json`, `effect/global-fetch(-in-effect)`, `effect/no-try-catch`, `effect/try-catch-in-effect-gen`, `effect/no-throw-statement`, `effect/no-new-error`, and the relevant global diagnostics. A second syntax implementation would lose type context and duplicate findings. |
| Yield a tagged/yieldable error directly instead of `Effect.fail(error)` | **Delegate to `effect/unnecessary-fail-yieldable-error`.** | Executor's `prefer-yield-tagged-error` is an existing `@effect/tsgo` rule with type-aware identification and a fix. |
| Infer types from Schema declarations rather than manually duplicate them | **Keep as guidance pending a provable contract.** | The principle is sound, but Executor's proximity/name heuristic can confuse distinct wire and domain types. A Doctor rule needs type-aware structural equivalence; local AST naming is insufficient. |
| Force Effect subpath namespace imports | **Reject as universal.** | It is a DXOS import and bundle convention. The Effect root package deliberately exports the same APIs, so this is not a correctness failure. |
| Forbid importing `makeX` service constructors; require Layers | **Reject as universal.** | The rule infers architecture from a name and exempts tests. Factory imports can be intentional, and not every `makeX` constructs a contextual Effect service. |
| Constrain `main.ts`, `*.schema.ts`, workflow files, package boundaries, SQL helpers, or ClickHouse compilation seams | **Keep project-local or expose as optional third-party integrations.** | These rules are valuable because they know a repository's modules and conventions. That same knowledge makes them inappropriate for a black-box verifier over arbitrary projects. |
| Biome/Vite+/ESLint/Oxlint correctness, import sorting, formatting, no `any`, and dependency boundaries | **Classify as broad TypeScript hygiene, not Effect semantics.** | These tools improve repositories but do not measure whether an agent wrote Effect correctly. Effect Doctor may report its general engine diagnostics separately, but they should not inflate an Effect-specific score. |

## Recommendation

1. Keep the current layered model: `@effect/tsgo` for semantic/type-aware diagnostics, `oxlint-plugin-effect` for local structural rules, and a very small first-party gap layer.
2. Advance only `no-inline-schema-compile` from this survey into contract research. Its independent appearance in two production applications is the sole cross-repository convergence not already owned upstream.
3. Use community configurations to tune presets. The strongest current adopters do not agree on “enable everything”: Supabase and `effect-grammar` use recommended, while Company OS and System F start from correctness and select more. Effect Doctor's blocking preset should remain high-precision; broader guidance belongs in advisory or opt-in profiles.
4. Do not copy repository-specific plugins into Effect Doctor. Where a dependency publishes its own deterministic plugin, a future extension point can preserve that plugin's provenance and run it only when the dependency/configuration is present.
5. Re-run this survey periodically. The ecosystem is actively moving from language-service patching, native `tsgo`, and separate syntax linters toward the official type-aware Oxlint bridge; old configurations should not determine a permanent architecture.
